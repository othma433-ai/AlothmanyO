# WA Al-Othmany Android v2.1 Actions Engine Design

## Goal
Extend the stable v2.0 extraction core with resumable invite-join and controlled publishing workflows while preserving bounded memory, explicit verification, multi-package support, and durable recovery.

## Architecture
- Keep extraction engine and Room persistence unchanged except for DB schema expansion.
- Add a dedicated `ActionAutomationEngine` for JOIN and PUBLISH jobs.
- Add generic persistent `action_jobs` and `action_items` queues so actions resume after process/service recreation.
- Extend `WhatsAppUiBridge` with state-classified UI actions: detect invite state, click the exact discovered target with node/parent/child/gesture fallbacks, edit message input, click send, and verify state transitions.
- Maintain strict bounded waits and no unverified success states.

## Join flow
1. Persist invite URLs as ordered action items.
2. Open each URL in the selected WhatsApp package.
3. Classify UI as DIRECT, APPROVAL, COMMUNITY, ALREADY_MEMBER, REQUEST_SENT, INVALID, or UNKNOWN.
4. If actionable, click the exact target discovered by classification using same-node -> clickable parent -> clickable child -> gesture fallback.
5. Re-snapshot until the expected post-action state appears.
6. Persist item result and continue; failed/unknown items do not stop the whole queue.

## Publish flow
1. User supplies explicit group names and one message.
2. Persist each target as an action item.
3. Navigate to Groups, open exact group, re-verify chat identity.
4. Set message via `ACTION_SET_TEXT`, verify input contains the intended message.
5. Click the discovered Send target and verify the input clears / UI changes.
6. Apply bounded pacing between groups and persist each result.

## Safety and correctness constraints
- No approval bypasses, security bypasses, rate-limit bypasses, or private-database access.
- No mass-discovered target list is auto-published to; publishing uses only user-provided group names.
- Every loop has a deadline/bound.
- UI clicks are not success until post-state verification passes.
- Database writes are durable and idempotent by action item primary key.
- Existing extraction jobs remain recoverable after DB migration.
